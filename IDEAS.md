## Хочется

### Бэкап и импорт (записано 2026-09-06)

Цель: выгрузить всё хранилище к себе на диск, потом дополнять эту копию только новым, и уметь залить копию обратно (в пустой бакет после аварии или в другой инстанс).

**Формат копии = раскладка бакета.** Папка `backup/` повторяет R2 один в один: `photos/<ref>.jpg`, `previews/<ref>.jpg`, `albums/<id>/info.json`, плюс `trash/…` и `manifest.json` (дата, список альбомов, число объектов). Тот же формат, что у локального `r2/` для `cp_albums_local.sh`, то есть копия сразу поднимается в локальный dev без конвертации. Ничего не архивировать: папка с файлами проще проверять, дополнять и открывать глазами.

**Инкремент бесплатный.** Имя объекта уже есть хэш (`ref` = sha256 исходника), объекты иммутабельны, значит «что нового» = множество `ref` из всех `info.json` минус имена файлов в папке. Пересчитывать хэши не нужно, только сравнить списки; для контроля целостности хватает размера (`files[].size` или размер из листинга), потому что `ref` считается от исходника, а не от сохранённого JPEG, и локальный файл по нему не перепроверишь. `info.json` перезаписывать всегда (мелкие), фото и превью только отсутствующие. Удалённые из альбомов фото в копии оставлять (это же бэкап), опционально показывать «в копии есть N объектов, которых нет в бакете».

**Что не лежит в R2 и что тоже надо выгрузить:** счётчики просмотров живут в `AlbumInfoDO`. Экспорт: `GET album/<id>/stats` в `albums/<id>/stats.json`. Импорт: новый `PUT album/<id>/stats` поверх уже существующего `importStats` (action в DO есть, HTTP-ручки нет).

**Порядок при экспорте:** сначала все `info.json`, потом фото по списку из них, в конце ещё раз `info.json` тех альбомов, что изменились за время выгрузки. Тогда в копии каждый `ref` из любого `info.json` гарантированно есть (загрузка тоже пишет фото раньше `info.json`).

**Варианты реализации, от дешёвого к дорогому:**

1. **rclone / S3 API, ноль кода.** `rclone sync r2:ohmyphoto ./backup` делает ровно инкрементальную копию по размеру/ETag, `rclone copy ./backup r2:ohmyphoto` заливает обратно. Нужен R2 API token (read-only для бэкапа). Не покрывает статистику просмотров. Достаточно описать в README как «резервная копия для админа с терминалом». Стоит сделать в любом случае как нулевой уровень.

2. **Страница Backup в админке, Chromium.** `showDirectoryPicker()` даёт хэндл на папку; браузер читает список альбомов, сравнивает `ref` с содержимым `photos/`, докачивает недостающее через `FileSystemWritableFileStream` (как ZIP-загрузка в галерее, но на диск сразу, без ограничения по памяти). Worker ничего нового не строит, как и с ZIP: 10 ms CPU и 50 субзапросов не позволяют.
   - Нужно на сервере: `GET albums?files=1` (список уже читает каждый `info.json`, отдать `files` ничего не стоит), либо отдельный `GET backup/manifest?cursor=` поверх того же листинга. Опционально листинг `photos/` страницами по 1000 (одна страница = один субзапрос, с размерами и ETag) для проверки «в бакете есть объекты, на которые не ссылается ни один альбом» и для сверки размеров.
   - Скачивание фото: `GET album/<id>/raw/photos/<ref>` идёт через `RL_ADMIN_API` 60/мин, то есть 1000 фото = 17 минут минимум. Варианты: отдельный лимитер `RL_BACKUP` для `raw/*`, или качать через публичные подписанные `/img/…?s=` (админка уже умеет `imageSig`, лимит 300/мин, и edge cache помогает), но альбомы без секрета так не выгрузишь.
   - Fallback для Firefox/Safari (нет `showDirectoryPicker`): собирать дельту в ZIP через `public/zip.js` в Blob (ограничено памятью), а «что уже есть» брать из `manifest.json` предыдущей копии, который пользователь выбирает через `<input type=file>`; распаковать дельту поверх старой папки.

3. **Импорт из папки.** `<input type=file webkitdirectory>` работает везде, `showDirectoryPicker()` в Chromium. Существующих ручек почти хватает: `POST album` (или `PUT` при merge), `POST album/<id>/file` с `photo` + `preview` + `ref` (превью уже есть, конвертация в canvas не нужна, сервер пишет объект только если его нет), `POST album/<id>/files` для уже существующих `ref` (сначала `GET photo/<ref>`, как при обычной загрузке). Нового: `PUT album/<id>/stats`, и режим в UI: конфликт по `albumId` (пропустить / слить `files` / заменить `info.json` / залить под новым id), прогресс с возобновлением (импорт идемпотентен, повторный запуск докачивает пропущенное). Лимит 60/мин на админ-API тот же, 2 запроса на новое фото.

**Помнить:** в копии лежат секреты всех альбомов и через них подписываются ссылки на фото, так что папка бэкапа чувствительная, держать на зашифрованном диске. `wrangler r2 object get` по одному объекту для бэкапа не годится (нет sync), `wrangler r2 bucket` не умеет копировать бакеты.

**Порядок, если делать:** (1) README про rclone, (2) `GET albums?files=1` + страница Backup с инкрементальной выгрузкой в папку, (3) импорт из папки, (4) статистика (`stats.json`, `PUT stats`), (5) ZIP-fallback для не-Chromium.
